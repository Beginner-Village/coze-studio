# 猎鹰智能体 · 真实沙箱环境 + 技能自主执行 —— 分析报告

> 日期:2026-06-12
> 范围:调研报告(不含实现)。目标是把"技能怎么真实执行、智能体怎么自主规划+执行、沙箱怎么管理"这几个**尚未确定的点**分析清楚,给出可决策的方案与路线图。
> 参考开源:[TencentCloud/CubeSandbox](https://github.com/TencentCloud/CubeSandbox)、[cloudwego/eino](https://github.com/cloudwego/eino) ADK

---

## 0. 一句话结论

平台**已经有技能系统的骨架**(顶级技能页 + Skill 域 + agent 绑定 + `read_skill` 渐进式披露),但技能目前只是**一段 Prompt 文本 + 对已有 workflow/plugin 的引用**,没有真实文件、没有 bash、没有沙箱。要做到"像 LangChain/Claude 那样读写文件、自建技能、按技能跑 bash",需要补三层:**(A) 技能升级成带脚本文件的文件夹(MinIO 持久化)、(B) 真实沙箱运行时(CubeSandbox,E2B 兼容)、(C) agent 的文件/bash 工具 + 自主规划循环(Eino ReAct 现有,可选升级到 ADK Plan-Execute)**。并发用"**按 user_id 单活沙箱 + 四态生命周期 + MinIO 真相源 + Redis 注册表**"压住。

## 1. 现状盘点(已有的,即"之前那个计划"的产物)

### 1.1 技能系统(已存在,Prompt 编排形态)

| 组件 | 路径 | 现状 |
|---|---|---|
| 顶级技能管理页 | `frontend/apps/coze-studio/src/pages/space-skill` | ✅ 已和工作流同级 |
| Skill 域 | `backend/domain/skill/{entity,repository,service,internal/dal}` | ✅ DB 存储 |
| Agent 绑定技能 UI | `frontend/packages/agent-ide/tool/.../agent-skill-*` | ✅ 已有 |
| `read_skill` 工具 | `agentflow/node_tool_skill.go` | ✅ 渐进式披露:system prompt 只列技能名+描述,agent 按需 `read_skill(name)` 拿全文 |
| 技能内资源引用 | `agentflow/node_tool_skill_resources.go` | ✅ 技能 Prompt 里可引用 `workflow/plugin/knowledge`,运行时解析并挂载 |
| 系统提示渲染 | `agentflow/node_skills_render.go` | ✅ |

**关键限制 —— Skill entity 当前数据模型**(`backend/domain/skill/entity/skill.go`):
```go
type Skill struct {
    SkillID, SpaceID, CreatorID  int64
    Name, Description, Prompt    string   // ← 技能本体就是 Prompt 一段文本
    IconURI                      string
    CreatedAt, UpdatedAt         int64
}
```
> 没有脚本文件字段、没有 MinIO 文件 bundle。"执行"靠把 Prompt 注入大模型 + 引用已有平台资源。这正是要升级的地方。

### 1.2 智能体引擎(Go + Eino ReAct)

- **Eino 版本:`v0.4.7`**(`backend/go.mod`)。
- 单 agent 用 **`flow/agent/react`**(`agent_flow_builder.go:277` `react.AgentConfig{MaxStep:30}` → `react.NewAgent`)。这就是当前的"自主规划+执行"引擎:Reason → 调工具 → Observe → 循环,最多 30 步(≈15 轮工具调用)。
- 工具统一抽象为 `eino` 的 `tool.BaseTool`/`InvokableTool`,在 builder 里聚合:**plugin / workflow / database / memory(agent-variable) / external-knowledge / skill**。新增"文件/bash 工具"只需在同一处 append,**零侵入**。
- 已支持 **checkpoint + 中断恢复**(`compose.WithCheckPointID`,目前用于 OAuth 插件),为 human-in-the-loop / 长任务打好了基础。
- 流式输出走 `compose.Runnable[*AgentRequest, *schema.Message]`。

### 1.3 现有的 coderunner(无关但易混淆)

`backend/infra/{contract,impl}/coderunner` 有 `direct` + `sandbox` 两个实现,但它是给 **workflow 的"代码节点"**用的:**单次、无状态、每次 fork 一个 Python 子进程**(`impl/coderunner/sandbox/runner.go`),Deno 风格权限位(AllowRead/Write/Net/Run)。
> ⚠️ 这**不是**我们要的会话级沙箱,但它的 `contract/impl` 分层是很好的范本,新沙箱服务照此分层。

### 1.4 现成可复用的基础设施

| 能力 | 接口/路径 | 用途 |
|---|---|---|
| 对象存储(MinIO) | `infra/contract/storage` → `PutObject/GetObject/GetObjectUrl` | 技能 bundle + 用户 workspace 持久化 |
| Redis 缓存 | `infra/contract/cache` + `impl/cache/redis` | 沙箱注册表、single-flight 锁 |
| 对外智能体 API | `application/conversation/openapi_agent_run.go` | 沙箱挂钩点(见 §5) |

### 1.5 对外 API 的身份三层(持久化 key 的依据)

`ChatV3Request`(`api/model/conversation/run/run.go`)+ `openapi_agent_run.go`:

| 层级 | 字段 | 含义 | 备注 |
|---|---|---|---|
| 租户 | `apiKeyInfo.UserID`(creatorID) | API key 拥有者 = agent 所有者 | |
| **终端用户** | `ChatV3Request.User`(JSON `user_id`,**required**) | 注释原文:*"data isolation identification, need to ensure unique"* | **持久化 key** |
| 会话 | `ConversationID`(optional) | 一个 user 多个会话 | |

> 结论:**持久化按 `user_id`**(终端用户),不是 agent、也不是会话。实现上卷 key 建议用 `connector/agent_id + user_id` 组合防撞车。

## 2. CubeSandbox 分析

| 维度 | 结论 |
|---|---|
| 隔离技术 | **microVM**(RustVMM + KVM,独立 Guest 内核),硬件级隔离,杜绝容器逃逸。**需要 x86_64 + KVM 裸金属/可嵌套虚拟化**,普通 k8s pod 跑不了 |
| 冷启动 | 平均 **<60ms**(高并发 <150ms);预置资源池 + 快照克隆 |
| 内存开销 | **<5MB/实例**,单机可上千实例 |
| 持久化 | **CoW 快照引擎**(v0.3.0+),事件级快照回滚、fork、pause/resume |
| **API 兼容** | **E2B SDK drop-in**:shell 执行、文件 I/O、代码执行、网络策略、pause/resume —— **换一个 URL 环境变量即可迁移** |
| 部署 | 单机开箱即用;多机集群(CubeMaster)。非 k8s 原生 |
| 验证底座 | 你确认:**用一台真实物理机(KVM)** → 单机模式即可,理想 |

**对我们最大的价值 = E2B 兼容**:我们只要面向 **E2B 接口契约**编程,后端可在 `CubeSandbox(自建/高隔离)` ↔ `E2B 云` ↔ `Docker 容器(降级)` 之间切换,不锁死。

> ⚠️ Go 生态注意:E2B 官方 SDK 是 JS/Python。Go 侧要么直接调 E2B/Cube 的 **REST API**(推荐,接口稳定),要么找/封装 Go 客户端。这是一个落地细节,见 §8 风险。

## 3. 核心问题①:智能体怎么"自主规划 + 自主执行"?

这是你说"还没确定"的核心。有三条技术路线,对应 Eino 的不同能力层级:

### 路线 A:现有 ReAct(v0.4.7,零升级)
- 机制:大模型在 system prompt 里看到可用技能/工具,自己决定调哪个、`MaxStep:30` 内循环。
- 自主规划 = 模型隐式规划(没有显式 plan 产物)。
- **优点**:现成、零改动、流式/中断已通。**缺点**:复杂任务(多技能编排、长流程)容易步数爆 / 跑偏 / 无显式进度,不好做 "todo 追踪"。
- **适用**:技能数量不多、单技能任务为主的 MVP。

### 路线 B:升级 Eino → ADK,用 Plan-Execute / DeepAgents(推荐演进方向)
- **Eino ADK 在 `v0.5.0` 引入**(我们当前 v0.4.7 在其之前),提供:
  - **ChatModelAgent**:开箱即用 ReAct(平替现有)。
  - **Plan-Execute 模式**:`Planner 生成结构化步骤 → Executor 执行 → Replanner 评估/动态重规划`,专为"复杂任务分解+动态调整"设计。
  - **DeepAgents 模式**:主 Agent 用 ReAct,把目标拆成结构化 **todos**,通过统一 `TaskTool` 入口委派 **SubAgent**,**上下文隔离**(子 agent 在干净上下文里跑,不继承主 agent 的中间推理链)→ 这正是"自主规划+追踪进度"的标准答案。
  - **多智能体**:Supervisor / Transfer / Agent-as-Tool。
  - **Shared Session**:单次运行内跨 agent 的 KV 状态共享。
  - **Runner + AgentEvent** 事件流、**中断/Resume + CheckPointStore**(human-in-the-loop)。
- **优点**:显式规划、进度可见、上下文隔离、官方维护、和我们"技能=可复用能力单元"的心智天然契合(一个技能 ≈ 一个 SubAgent / 一个 TaskTool)。**缺点**:需要从 v0.4.7 升级(API 有变动,需评估迁移成本);ADK 部分组件标 beta。
- **适用**:技能会越来越多、要做"智能体自己挑技能、按计划一步步跑"的目标形态。

### 路线 C:不动 Eino,在沙箱里跑"agentic 脚本"
- 把规划/执行下放到沙箱内的一个进程(例如沙箱里跑一个 mini-agent/脚本),主 agent 只下发目标。
- **优点**:解耦。**缺点**:重复造 agent 循环、可观测性差、和现有 Eino 体系两张皮。**不推荐**。

> **报告建议**:**MVP 用路线 A**(现有 ReAct + 新增文件/bash 工具,快速验证"沙箱真能跑技能");**目标形态走路线 B**(升级 ADK,用 DeepAgents/Plan-Execute 做真正的自主规划)。两者工具层完全复用,升级是平滑的。**Eino 升级评估单独立项**(见 §7 风险)。

## 4. 核心问题②:技能怎么"真实执行"?

### 4.1 技能数据模型升级(DB + MinIO)

把"Prompt 一段文本"升级成"**文件夹 bundle**":

```
skill bundle (MinIO: skills/{skill_id}/{version}/)
├── SKILL.md          # 描述 + 给模型的指令(= 现有 Prompt 字段平滑迁移)
├── scripts/
│   ├── run.sh
│   └── do_x.py
└── assets/...        # 可选资源
```

- **DB**(Skill entity 扩展):增 `BundleURI`(MinIO 前缀)、`Manifest`(文件清单+各文件 hash)、`Version`/`ContentHash`、`EntryPoints`(声明可执行入口,如 `scripts/run.sh`)、`Runtime`(python/node/bash)。
- **MinIO**:存实际文件,key 用内容寻址(hash),天然支持 dedup 与版本。
- **兼容**:现有 `Prompt` → `SKILL.md`,老技能无脚本时退化为纯指令技能(行为不变)。
- **前端**:`space-skill` 页加一个**文件编辑器**(SKILL.md + 脚本树),保存即上传 MinIO + 写 manifest。

### 4.2 技能注入沙箱(运行时)

会话首次需要时,沙箱会话管理器:
1. 确保 user_id 的活沙箱存在(§5)。
2. 把该 agent **绑定的技能 bundle** 同步进沙箱 `/skills/<skill_name>/`(只读)。
3. **dedup**:按 bundle `ContentHash` 比对沙箱内已注入清单,**已是同版本就跳过**;有新版本则增量覆盖。
4. 把技能清单写进 system prompt(复用现有 `node_skills_render` + `read_skill`)。

### 4.3 三种执行触发方式(可叠加)

| 方式 | 模型怎么用 | 落地 |
|---|---|---|
| **指令型**(现有) | `read_skill(name)` 读 SKILL.md,模型照着做 | 已有,保留 |
| **脚本型**(新) | 模型调 `run_bash("bash /skills/x/scripts/run.sh --arg ...")` | 新增 bash 工具 |
| **能力型**(新,自由) | 模型用 `write_file`/`read_file`/`run_bash` 在 `/workspace` 自由读写、临时造脚本、跑命令(类 LangChain/Claude) | 新增文件工具 |

### 4.4 新增 agent 工具(Eino InvokableTool,挂在 builder 同一处)

| 工具 | 作用 | 落点 |
|---|---|---|
| `run_bash(cmd, timeout?)` | 在沙箱执行 shell,返回 stdout/stderr/exit | → 沙箱会话管理器 |
| `read_file(path)` / `write_file(path, content)` | 读写沙箱文件 | 同上 |
| `list_files(path)` | 列目录 | 同上 |
| (可选) `create_skill(...)` | 把当前 workspace 产物沉淀成新技能(写回 DB+MinIO) | 进阶 |

> 沙箱目录约定:`/workspace`(user_id 持久区,跨会话)、`/skills/<name>`(注入只读)、`/conversations/<conv_id>`(单会话临时区)。

## 5. 核心问题③:沙箱生命周期 + 高并发设计

### 5.1 活沙箱粒度 = **按 user_id 一个**(不是按会话)

- 理由:持久化本来就 user_id 维度;一个用户极少真正并发跑两个会话。
- 同一沙箱内多会话靠子目录隔离;工具执行用 **per-sandbox 锁串行化**。
- 效果:**活沙箱数 = 活跃用户数**,把"每会话一个会爆"压下来。
- (若确有用户级高并发会话需求,二期再演进为"共享持久卷 + 多临时沙箱",当前 YAGNI。)

### 5.2 四态生命周期

```
       ┌─────────┐  无活沙箱   ┌──────────┐
请求 ─▶│  冷启动  │───────────▶│   活跃    │◀───── 复用(只补同步新技能)
       └─────────┘            └────┬─────┘
   base 快照克隆(<60ms)            │ 闲置 ~5-10min
   + MinIO 拉 workspace            ▼
   + 注入技能(dedup)         ┌──────────┐  下条消息
                            │  挂起     │──────────▶ resume(秒级)
                            │ (pause)   │
                            └────┬─────┘
                                 │ 更久闲置 / 内存压力 / LRU
                                 ▼
                            ┌──────────┐
                            │  回收     │  workspace 刷回 MinIO + kill
                            └──────────┘
```

- **冷启动**:从预烘焙 **base 快照**(预装 python/node/常用依赖)克隆 → 从 MinIO 拉该 user 的 workspace → 注入绑定技能(hash dedup)。目标整体 **1–2s**。
- **热复用**:活沙箱在 → 直接用,仅补同步新增/变更的技能。
- **挂起**:闲置阈值(默认 5–10min,可配)→ CubeSandbox `pause`(CoW)释放内存,`resume` 秒级。
- **回收**:更长闲置 / 节点内存压力 / 超出池上限 → 先挑冷的 LRU,workspace 刷回 MinIO 后 kill。

### 5.3 持久化 = **MinIO 为真相源**

- 沙箱本地 FS = 工作副本;CubeSandbox 节点快照 = **快恢复缓存**(不耐节点重启,不能当真相源)。
- **写回**:每轮结束 / 技能写文件后,**增量 tar `/workspace` → MinIO**(内容 hash 跳过未变);回收时最终 flush。
- **恢复**:冷启动从 MinIO 拉。
- key:`workspaces/{connector_or_agent_id}/{user_id}/...`。

### 5.4 并发护栏

| 机制 | 说明 |
|---|---|
| 节点有界池 | 按内存预算限活沙箱数;超限 LRU(先 pause 再 kill) |
| **single-flight** | 同 user_id 冷启动加锁(Redis),两条消息同时来不会建两个沙箱 |
| 沙箱注册表 | `user_id → {sandboxID, node, state, lastActive}` 存 **Redis**,survive 重启、为多节点留路 |
| 空闲回收器 | 后台 goroutine 定期扫注册表,按阈值 pause/回收 |
| 配额 | 每 user 单沙箱;可加 CPU/内存/超时/磁盘上限(CubeSandbox 原生支持) |

## 6. 目标架构(分层 + 数据流)

```
┌────────────────────────────────────────────────────────────────┐
│ 对外 OpenAPI  /v3/chat (user_id, conversation_id)                │
│   openapi_agent_run.go  ──► 取 user_id, agent 绑定技能列表        │
└───────────────────────────────┬────────────────────────────────┘
                                 ▼
┌────────────────────────────────────────────────────────────────┐
│ Agent 引擎 (Eino)                                                │
│  ReAct(现) / ADK Plan-Execute·DeepAgents(目标)                  │
│  工具: plugin/workflow/db/memory/knowledge/skill                 │
│        + 新增 run_bash / read_file / write_file / list_files     │
└───────────────────────────────┬────────────────────────────────┘
                                 ▼ (工具调用)
┌────────────────────────────────────────────────────────────────┐
│ 沙箱会话管理器 (新, application/service 层)                       │
│  · ensureSandbox(user_id)  四态生命周期 + single-flight          │
│  · syncSkills(agent)  dedup 注入                                 │
│  · exec/read/write  → 转发到沙箱                                  │
│  · checkpoint workspace → MinIO                                  │
│  状态: Redis 注册表    真相源: MinIO                              │
└──────────┬───────────────────────────────┬─────────────────────┘
           ▼                                ▼
┌──────────────────────┐        ┌────────────────────────────────┐
│ infra/contract/sandbox│        │ infra/contract/storage (MinIO) │
│  Runner 接口          │        │  技能 bundle + user workspace  │
│  impl/cube (E2B REST) │        └────────────────────────────────┘
│  impl/docker (降级)   │
└──────────┬───────────┘
           ▼
   CubeSandbox 单机 (KVM microVM, 真实物理机)
```

**新增代码落点(沿用现有分层惯例)**:
- `backend/infra/contract/sandbox/` —— Runner 接口(Create/Exec/Read/Write/Pause/Resume/Kill/Connect)。
- `backend/infra/impl/sandbox/cube/` —— E2B 兼容 REST 客户端;`.../docker/` —— 降级后端(可选)。
- `backend/domain/sandbox/`(或 `application/sandbox/`)—— 会话管理器:生命周期、注入、注册表、持久化。
- `backend/domain/skill/` —— 扩展 entity(bundle/manifest/version)、service(上传/打包/取 bundle)。
- `agentflow/node_tool_sandbox.go` —— 4 个新工具,在 `agent_flow_builder.go` append。
- `frontend/.../space-skill` —— 技能文件编辑器。

| **P2 会话管理器** | user_id 单沙箱 + 四态生命周期 + Redis 注册表 + MinIO workspace 持久化 + single-flight | 同 user 跨会话 workspace 保留;冷启/挂起/回收可观测 |
| **P3 工具接入(ReAct)** | `run_bash/read_file/write_file/list_files` 挂进 builder;沙箱里能跑通一个真实任务 | 智能体能自主读写文件+跑命令(路线 A) |
| **P4 技能 bundle** | Skill entity 升级(bundle/manifest/version);`space-skill` 文件编辑器;运行时 dedup 注入 | 平台配脚本技能,agent 绑定后沙箱内可执行 |
| **P5 自主规划(ADK)** | 升级 Eino,引入 Plan-Execute / DeepAgents,技能↔SubAgent/TaskTool 映射 | 复杂任务自主拆解+追踪进度(路线 B) |
| **P6 加固** | 配额/超时/磁盘上限、并发压测、安全审计、可观测(接 obs-stack) | 高并发达标 |

## 9. 风险与未决问题

1. **Eino 升级成本(最大不确定)**:v0.4.7 → v0.5.x(ADK)的 API 变动面、对现有 workflow/agent 流的影响,需一次专门的迁移评估(P0)。可先不升、用 ReAct 跑通 P1–P4。
2. **Go ↔ 沙箱客户端**:E2B 官方 SDK 无 Go 版,需直调 REST 或自封装薄客户端;CubeSandbox 的 E2B 兼容度需实测(尤其 pause/resume、文件批量、长连接 exec)。
3. **CubeSandbox 成熟度/运维**:KVM 裸金属依赖、单机→多机扩展、快照与 MinIO 真相源的一致性策略,需 PoC 验证。
4. **持久化一致性**:沙箱本地 FS / 节点快照 / MinIO 三者一致性;并发写同一 user workspace(多会话)的冲突策略(当前用 per-sandbox 锁串行化)。
5. **安全边界**:技能脚本可执行任意 bash → 必须靠沙箱隔离 + 网络策略(CubeVS/eBPF) + 资源配额;`create_skill` 若开放给运行时,需审核机制。
6. **冷启动体验**:1–2s 目标依赖 base 快照预热 + workspace 增量;首次大 workspace 用户可能慢,需 lazy mount / 后台预热。

## ★ 11. 技能机制全貌(Anthropic Agent Skills)与我们的差距 —— 全文核心

> 这一节是重点。结论先行:**Agent Skills 这套机制的全部价值(渐进式披露 + 可执行脚本)本质上要求一个"文件系统 + bash 执行"的环境。所以沙箱不是配角,它是让"真实技能"成立的地基。** 我们现在缺的恰恰是 L3(脚本)和执行层。

### 11.1 一个 Skill 到底是什么

**Skill = 一个目录**,核心是 `SKILL.md`(YAML frontmatter + Markdown 正文),可选挂脚本/参考/资源:

```
my-skill/
├── SKILL.md        # 必需:YAML frontmatter(name, description) + Markdown 指令正文
├── scripts/        # 可选:可执行代码(Python / Bash / JS)
├── references/     # 可选:补充文档(大段细节,按需加载)
└── assets/         # 可选:模板 / 图片 / 数据文件
```

`SKILL.md` 头部:
```markdown
---
name: pdf-form-filler
description: 当用户要填写/解析 PDF 表单时使用。提取字段、按值回填、导出。
# (Claude Code 生态还支持 allowed-tools 等可选元数据)
---
# PDF 表单处理
... 给模型看的操作指令 ...
需要时运行 `python scripts/extract_fields.py <file>` 拿到字段清单。
```

### 11.2 三级渐进式披露(Progressive Disclosure)—— 机制的灵魂

| 级别 | 加载时机 | 加载内容 | 进入上下文? | 我们现状 |
|---|---|---|---|---|
| **L1 发现** | 启动时(system prompt) | 仅每个技能的 `name` + `description` | 是(很省) | ✅ `node_skills_render.go` 已做 |
| **L2 激活** | 任务匹配某技能时 | 该技能完整 `SKILL.md` 正文 | 是 | ✅ `read_skill(name)` 已做(但读的是 DB 的 `Prompt` 字段,不是真文件) |
| **L3 执行/细节** | 跑到具体步骤时 | 按需读 `references/*`、**跑 `scripts/*`** | 视情况:脚本**执行结果**可不入上下文 | ❌ **完全缺失**(无文件、无脚本、无 bash) |

> 实测数据:三级披露相比"全文塞进单 prompt",**平均 token ↓约 40%,任务准确率 ↑约 15–20%**。这就是为什么不能简单把所有技能正文一股脑塞进 system prompt。

### 11.3 脚本的两种身份(关键设计点)

`scripts/` 里的代码有**两种用法**,SKILL.md 要写清楚让模型区分:

1. **可执行(Executable)**:模型通过 **bash 直接运行**(如 `python scripts/extract.py`),**脚本本身和处理的数据都不进上下文**,只拿结果 → 确定性高、省 token(适合 PDF 解析、数据处理、调 API 这类确定逻辑)。
2. **参考(Reference)**:把代码**读进上下文**当文档/范例,模型照着改写。

> 这正是"像 langchain/claude 那样跑 bash"的落点:**L3 的可执行脚本 = `run_bash` 工具在沙箱里跑技能目录下的脚本**。没有沙箱 = L3 不存在 = 技能退化成纯 prompt(就是我们现在的样子)。

### 11.4 我们的技能系统 vs 标准 Agent Skills(精确差距表)

| 机制要素 | 标准 Agent Skills | 我们现状 | 要做的改造 |
|---|---|---|---|
| 技能载体 | 目录(SKILL.md + 文件) | DB 里一个 `Prompt` 字符串 | Skill entity 加 **bundle(MinIO)+ manifest** |
| L1 发现 | name/description 进 prompt | ✅ 已有 | 保留 |
| L2 激活 | 读真实 SKILL.md | ✅ `read_skill` 读 Prompt | `Prompt` → `SKILL.md`,从 bundle 读 |
| L3 参考文件 | 按需读 `references/*` | ❌ 无 | `read_file` 工具读沙箱内技能目录 |
| **L3 可执行脚本** | **bash 跑 `scripts/*`** | ❌ 无 | **沙箱 + `run_bash`**(核心) |
| 执行环境 | filesystem + code execution | ❌ 无 | **CubeSandbox**(地基) |
| 技能内引用 | 文件相对路径 | 引用 workflow/plugin/knowledge(`node_tool_skill_resources.go`) | **两种模型共存**:平台资源引用 + 真实脚本 |
| 持久化/版本 | git 目录 | DB 行 | MinIO 内容寻址 + version |
| 安全 | 信任 + 人工审计 | —— | **靠沙箱隔离 + 网络策略 + 配额**兜底 |

> **最关键的一行**:我们已经有 L1+L2(技能的"嘴"——会描述、会读指令),但**完全没有 L3 和执行环境(技能的"手"——会真的动文件、跑命令)**。补齐 L3 = 补沙箱 + 文件/bash 工具 + 技能 bundle。三者缺一不可,且都服务于"技能"这一个目标。

### 11.5 我们的独特点:技能里既有"脚本"也有"平台资源引用"

标准 Agent Skills 的技能只引用**目录内文件**。我们已有的 `node_tool_skill_resources.go` 让技能 Prompt 能引用**平台级 workflow/plugin/knowledge**。这是我们的增量优势,应**保留并与脚本模型共存**:

- 一个技能的 SKILL.md 里可以同时:① 指示模型调某个 workflow/plugin(走现有编排);② 指示模型 `run_bash` 跑 `scripts/x.sh`(走新沙箱)。
- 即"**编排型技能**"(复用平台能力)+ "**脚本型技能**"(沙箱里跑代码)统一在一个技能载体里,由 SKILL.md 描述何时用哪个。

### 11.6 落到执行流(端到端一条链)

```
终端(user_id) ─chat─▶ openapi_agent_run
  └─ agent 绑定技能列表(L1: name+desc 注入 system prompt)        ← 已有
       └─ 模型判断要用 skill X → read_skill(X)  (L2: 读 SKILL.md)   ← 已有(改读 bundle)
            └─ SKILL.md 指示:run_bash("python /skills/X/scripts/run.py")
                 └─ 沙箱会话管理器: ensureSandbox(user_id) → 注入 X 的 bundle(dedup)
                      └─ CubeSandbox 执行 → 结果回模型(脚本本身不入上下文)  ← L3 新增
                           └─ 产物写 /workspace → 增量回 MinIO(持久化)        ← 新增
```
