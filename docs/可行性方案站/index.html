沙箱环境 + 技能自主执行

现有技能系统已经会「说」——能描述、能读指令;但还不会「动」——不能真读写文件、跑 bash、执行脚本。本方案基于 cloudwego/eino 架构,接入 CubeSandbox 真实沙箱,补齐 Agent Skills 的执行层,让智能体能像 LangChain/Claude 那样自主规划、自主执行。

01

一句话结论

平台已经有技能系统的骨架,但技能目前只是一段 Prompt 文本。要做到「读写文件、跑 bash、自建技能」,关键洞察只有一句:

Agent Skills 这套机制的全部价值——渐进式披露 + 可执行脚本——本质上要求一个「文件系统 + bash 执行」的环境。所以沙箱不是配角,它是让「真实技能」成立的地基。

要补的能力 A

技能带真实脚本

Skill 从「一个 Prompt 字段」升级为「SKILL.md + 脚本文件夹」,DB 存元数据,MinIO 持久化文件 bundle。

要补的能力 B

真实沙箱运行时

CubeSandbox 单机 microVM(KVM),E2B 兼容接口。冷启动 / 挂起 / 回收 / 持久化全生命周期。

要补的能力 C

文件 / bash 工具 + 规划

给 Eino agent 挂 run_bash / read_file / write_file 工具;规划用现有 ReAct,目标态升级 ADK Plan-Execute。

02

技能机制全貌 · Agent Skills

一个 Skill = 一个目录:SKILL.md(YAML frontmatter + 指令正文)+ 可选脚本/参考/资源。它的灵魂是三级渐进式披露——按需加载,而不是把所有技能一股脑塞进上下文。

pdf-form-filler/SKILL.md技能载体
---
name: pdf-form-filler
description: 当用户要填写/解析 PDF 表单时使用。
# 仅 name+description 进 system prompt(L1)
---
# PDF 表单处理
... 给模型看的操作指令(L2:read_skill 时载入) ...
需要时运行 `python scripts/extract.py <file>`
# L3:脚本在沙箱里跑,结果回模型,脚本本身不入上下文
目录结构filesystem 必需
my-skill/
├── SKILL.md        # 必需 · frontmatter + 指令
├── scripts/        # 可执行代码 (py/sh/js)
│   ├── run.sh
│   └── extract.py
├── references/     # 按需加载的细节文档
└── assets/         # 模板 / 数据文件

// 实测:三级披露相比全文塞 prompt
// token ↓ ~40% · 准确率 ↑ ~15-20%
L1
发现 · Discovery

启动时载入

只把每个技能的 name + description 放进 system prompt,刚好够模型判断「何时该用」,几乎不占上下文。

✓ 我们已有 node_skills_render.go
L2
激活 · Activation

匹配时读全文

任务命中某技能 → 模型调 read_skill(name) 把完整 SKILL.md 正文读进上下文。

✓ 我们已有 但读的是 DB 的 Prompt 字段
L3
执行 · Execution

跑脚本 / 读细节

按需读 references/*、用 bash 跑 scripts/*;脚本执行结果可不入上下文(确定性高、省 token)。

✗ 完全缺失 无文件 · 无 bash · 无沙箱
!

我们已经有 L1+L2(技能的「嘴」——会描述、会读指令),但完全没有 L3 和执行环境(技能的「手」——会真的动文件、跑命令)。补齐 L3 = 补沙箱 + 文件/bash 工具 + 技能 bundle,三者缺一不可,且都服务于「技能」这一个目标。

04

CubeSandbox 深度解读

腾讯云开源的「AI 智能体专用沙箱服务」——即时、并发、安全、轻量。用 microVM(独立内核)给每个智能体一个真正隔离的执行环境,却有接近容器的启动速度和远低于容器的内存开销。这是本方案的执行地基。

出品 腾讯云 Tencent Cloud 协议 Apache 2.0 最新 v0.3.1 · 2026-06 隔离 RustVMM + KVM microVM 接口 E2B SDK drop-in

它一次性解决了「安全隔离」和「资源效率」这对长期矛盾:独立 Guest 内核杜绝逃逸,<5MB 内存 + <60ms 冷启动让单机能跑上千个沙箱。

八大组件 · 一次创建沙箱的全链路

REST 网关 → 集群调度 → 节点生命周期 → microVM 启动 → 网络策略 → 隔离执行。

为什么快、为什么省 · 三方对标

Rust 重写 + 极致裁剪运行时 + CoW 内存复用 + 预置资源池,把「VM 级隔离」做到了「容器级开销」。

维度Docker 容器传统虚拟机CubeSandbox
隔离强度低 · 共享内核高 · 独立内核极致 · 独立内核 + eBPF
冷启动~200ms数秒<60ms(50 并发 67ms · P99 137ms)
单实例内存~200MBGB 级<5MB(规格 ≤32GB 均成立)
单机密度数百数十数千
逃逸风险有(命名空间)无无 · 硬件级
快照粒度—整机/慢事件级 · 毫秒
持久化 · CubeCoW

事件级快照 + 秒级克隆

v0.3.0 引入的 CoW 引擎:毫秒粒度快照、回滚到任意检查点、从模板瞬间 fork 出并行环境。正好对应我们的「挂起/恢复 + 持久化」生命周期。

网络 · CubeVS

eBPF 内核级隔离

虚拟交换 + 沙箱间流量过滤 + 严格出站策略。技能脚本能跑任意 bash,安全边界就靠它 + 独立内核兜底。

兼容 · E2B

换个 URL 就迁移

原生兼容 E2B SDK 接口,drop-in 替换,业务逻辑零改动。意味着我们面向 E2B 契约编程,后端可在 Cube / E2B 云 / Docker 间切换,不锁死。

部署模式 + 要求

三种部署 · 门槛比想象低

06

沙箱生命周期 + 高并发

活沙箱按 user_id 一个(不是按会话)。同一沙箱内多会话靠子目录隔离 + per-sandbox 锁串行化。活沙箱数 = 活跃用户数,把「每会话一个会爆」压下来。

真相源

MinIO 为准

沙箱本地 FS = 工作副本;节点快照 = 快恢复缓存(不耐重启)。每轮结束/写文件后增量 tar workspace → MinIO,hash 跳过未变。

并发护栏

single-flight + 注册表

同 user_id 冷启动加锁(Redis),两条消息不会建两个沙箱。注册表 user_id→{sandboxID,state} 存 Redis,survive 重启。

有界池

LRU 回收

节点按内存预算限活沙箱数;超限先挑冷的 LRU,pause 再 kill。可加 CPU/超时/磁盘配额(CubeSandbox 原生)。

07

端到端执行时序

一条「终端用户触发脚本型技能」的完整链路。注意脚本执行结果回模型,脚本本身不入上下文(L3 的省 token 关键)。

风险与未决

最大不确定

Eino 升级成本

v0.4.7 → v0.5.x(ADK)API 变动面、对现有 workflow/agent 流的影响,需专门迁移评估(P0)。可先不升,用 ReAct 跑通 P1-P4。

客户端

Go ↔ 沙箱

E2B 官方无 Go SDK,需直调 REST 或封薄客户端;CubeSandbox 的 E2B 兼容度(尤其 pause/resume、批量文件、长连 exec)需实测。

成熟度

CubeSandbox 运维

KVM 裸金属依赖、单机→多机扩展、快照与 MinIO 真相源的一致性策略,需 PoC 验证。

一致性

持久化冲突

沙箱本地 FS / 节点快照 / MinIO 三者一致性;并发写同一 user workspace(多会话)用 per-sandbox 锁串行化。

安全

任意 bash 边界

技能脚本可执行任意命令 → 必须靠沙箱隔离 + 网络策略(CubeVS/eBPF)+ 资源配额;create_skill 若开放需审核。

体验

冷启动延迟

1-2s 目标依赖 base 快照预热 + workspace 增量;首次大 workspace 用户可能慢,需 lazy mount / 后台预热。
